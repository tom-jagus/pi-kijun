# Documentation

Make documents useful without duplicating code or other docs. Follow the global
contract for authority, factual checks, prose review, and documentation timing.
Inspect existing documents and relevant sources before changing claims, commands,
links, or legal information. Verify actual files rather than proposals.
Behaviour-defining Markdown follows `development`, not documentation authority.

## README convention

Keep a simple shape; combine headings or omit inapplicable sections rather than
filling templates with placeholders:

1. **Overview:** Explain what the repository contains and why it exists.
2. **Get started:** Give prerequisites and the shortest working install/run path,
   with commands verified against the repository.
3. **Usage:** Show a minimal example or explain use without repeating the manual.
4. **Documentation:** Link to useful guides without duplicating their content.
5. **License and copyright:** Name the actual license and link its file. Include
   copyright only with confirmed attribution. Ask about unknown license, holder,
   or year rather than inventing them or assuming public source is licensed.

Add badges, screenshots, contribution instructions, status notes, or sponsor
links only when relevant and supported; never add empty placeholders.

## Other documentation

Write for a clear audience and purpose. Prefer short explanations and links to
authoritative sources over repeated facts. Use `brainstorming` for charter and
brief outcomes, and `work-items` with the relevant activity for project records.
Do not turn activity results into extra guides or parallel progress reports.
Report changed paths and remaining uncertainty for editor review. Writing a
draft does not accept a material decision.
