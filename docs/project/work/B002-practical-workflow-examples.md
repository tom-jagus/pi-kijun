# Practical workflow examples

## Outcome

Make common Kijun interactions easier to understand through short conversation
examples in the existing workflow guide.

## Why

The contract and guide explain the rules, but provide few examples of requests
and expected responses. Concrete examples would help the user express intent
and recognize whether Pi is respecting the workflow.

## Boundaries

Illustrate the existing rules rather than introduce new authority or required
commands. Keep examples in the existing guide and link to authoritative rules
where needed. Do not create another skill or a formal behavioural test suite.

## Acceptance criteria

- Examples demonstrate a small manual-first fix without project records and
  explicit Pi-edit approval for a bounded change.
- Examples distinguish implementation permission, user acceptance, subsequent
  documentation maintenance, and separately requested Git actions.
- A brainstorming example ends without automatically creating work records.
- Each example makes the expected action or stopping point clear without
  repeating the full governing policy.
- Examples agree with the current contract and skills and do not imply that
  illustrative wording is a required command or an enforcement guarantee.
